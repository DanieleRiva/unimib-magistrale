## La traccia reale sotto esame

L'obiettivo dell'assignment era applicare l'**Esecuzione Simbolica Pura** al metodo `computeFinalBalance` per studiare formalmente se le esecuzioni che completano il ciclo `while` **esattamente due volte** possano o meno causare una vulnerabilità di **Buffer Overflow alla riga 8**[cite: 89].

Il codice ufficiale della consegna prevede le seguenti istruzioni[cite: 89]:

```java
public static double computeFinalBalance(double[] transactions, int count) {
    double balance = 0.0;          // Line 1
    int i = 0;                     // Line 2
    boolean overdrawn = false;     // Line 3
    double minimum = balance;      // Line 4
    int steps = 0;                 // Line 5

    while (i < count && !overdrawn) {        // Line 6 - ATTENZIONE QUI!
        steps = steps + 1;                   // Line 7
        double amount = transactions[i];     // Line 8 - Riga critica sotto analisi
        balance = balance + amount;          // Line 9
        boolean isNegative = (balance < 0);  // Line 10
        if (isNegative) {                    // Line 11
            overdrawn = true;                // Line 12
            minimum = balance;               // Line 13
        }
        i = i + 1;                           // Line 15
    }

    if (overdrawn) {                         // Line 16
        minimum = 0.0;                       // Line 17
    }

    return minimum;                          // Line 18
}
```

La traccia imponeva di mappare le variabili del codice usando le seguenti identità simboliche maiuscole[cite: 89]:
* `balance` = `B`, `i` = `I`, `overdrawn` = `O`, `minimum` = `M`, `steps` = `S`, `count` = `C`, `amount` = `A`, `isNegative` = `IN`.

## Lo svelamento del 9/10: L'inganno della riga 6

Se analizziamo il commento di feedback lasciato dal professore Alind Xhyra nella correzione ufficiale della piattaforma, leggiamo testualmente:
**"A buffer overflow is possible if the array transaction has only one element."**

*Perché ti ha tolto un punto?* Nella tua risposta scritta alla domanda Q3 (in cui dovevi dimostrare l'assenza o la presenza del buffer overflow), hai concluso dicendo che l'accesso è matematicamente sicuro ed è protetto dalla Path Condition (`UNSAT`) assumendo implicitamente come precondizione naturale che `count <= transactions.length`[cite: 95, 103]. 

Tuttavia, l'esecuzione simbolica rigorosa deve operare in modalità **Zero-Inference**, ovvero basandosi *esclusivamente* sulle condizioni scritte nel codice, senza inventarsi precondizioni di buon senso che il programmatore non ha inserito. 

Guardiamo con attenzione la riga 6 del codice di questo assignment:
`while (i < count && !overdrawn)`

Noti qualcosa? **Manca completamente il controllo sui confini dell'array!** Il programmatore si è dimenticato di scrivere `&& i < transactions.length` (controllo che, non a caso, apparirà poi nell'assignment successivo W11). 

Di conseguenza, se l'array fornito in ingresso ha una lunghezza pari a 1 (`transactions.length = 1`) ma il parametro `count` è impostato a 2 (`C = 2`), il motore simbolico traccia questo scenario:
1. **Iterazione 1 (`I = 0`):** La guardia del ciclo verifica `0 < 2 && !false` $\rightarrow$ Superata[cite: 89]. Alla riga 8 viene eseguito `transactions[0]`. L'indice `0` è minore della lunghezza dell'array (`1`), quindi l'accesso è **sicuro**[cite: 89, 98]. Supponiamo che la transazione sia positiva, quindi `overdrawn` resta falso ed `i` cresce a `1`[cite: 91, 92].
2. **Iterazione 2 (`I = 1`):** La guardia del ciclo verifica `1 < 2 && !false` $\rightarrow$ **Superata di nuovo!** [cite: 92] Il flusso entra nel ciclo ed esegue la riga 8: `transactions[1]`[cite: 93]. Ma la lunghezza dell'array è `1`. L'indice `1` è fuori dai limiti dell'array (`1 >= 1`). **BUFFER OVERFLOW!**

L'SMT Solver, analizzando la formula di violazione `PC && !(I < transactions.length)`, avrebbe risposto **`SAT`** producendo esattamente il controesempio `transactions.length = 1` e `count = 2`. Concludere dicendo che il buffer overflow era impossibile in modo assoluto ti è costato il punto della lode.

## Svisceramento dell'Excel: Analisi riga per riga del cammino (2 Iterazioni)

Vediamo come si popolano matematicamente le colonne del tuo file Excel per dimostrare la perfetta comprensione del tracciamento algebrico delle due iterazioni[cite: 89].

### 1. Fase di Inizializzazione (Linee 1 - 5)
* **Linea 1:** La variabile `balance` riceve il valore `0.0`. Stato: `B = 0.0`. PC = `TRUE`[cite: 89].
* **Linea 2:** `i` viene inizializzata a `0`. Stato: `I = 0`[cite: 89].
* **Linea 3:** `overdrawn` viene impostata a `false`. Stato: `O = FALSO`[cite: 89].
* **Linea 4:** `minimum` copia il valore di `balance`. Stato: `M = 0.0`[cite: 89].
* **Linea 5:** `steps` viene azzerata. Stato: `S = 0`. Il valore di `count` riflette l'input simbolico: `C`[cite: 89].

### 2. Prima Iterazione del Ciclo
* **Linea 6 (Valutazione Guardia):** Il motore valuta `i < count && !overdrawn`. Sostituendo i valori correnti dello stato, otteniamo `0 < C && !false`, che si riduce a `C > 0`. Per entrare nel ciclo, questa condizione deve essere vera.
  * PC Aggiornata: `C > 0`[cite: 89].
* **Linea 7:** Incremento degli step. Stato: `S = 1`[cite: 89].
* **Linea 8 (Accesso Array):** Viene campionato l'elemento all'indice `i = 0`. Il valore simbolico assegnato alla variabile `amount` è `A[0]`[cite: 89].
* **Linea 9:** Il bilancio viene aggiornato: `balance = balance + amount`. Sostituendo i valori dallo stato (`0.0 + A[0]`), lo stato simbolico di `balance` diventa `A[0]`[cite: 90].
* **Linea 10:** Viene valutata l'espressione booleana `isNegative = (balance < 0)`. Sostituendo il valore corrente di `balance`, lo stato simbolico di `IN` diventa `(A[0] < 0)`[cite: 90].
* **Linea 11 (`if isNegative`):** Per garantire che il ciclo non si interrompa e possa completare una seconda iterazione, l'esecuzione simbolica deve forzare lo scenario in cui `isNegative` sia **Falso** (ovvero la transazione non deve mandare il conto in rosso)[cite: 103]. La PC accumula questo vincolo tramite l'operatore di negazione[cite: 91]:
  * PC Aggiornata: `C > 0 && A[0] >= 0`[cite: 91].
* **Linea 15:** L'indice viene incrementato: `i = i + 1`. Stato: `I = 1`[cite: 92].

### 3. Seconda Iterazione del Ciclo
* **Linea 6 (Valutazione Guardia):** Il motore valuta nuovamente la condizione con il nuovo stato (`I = 1`). L'equazione è `1 < C && !false`. Affinché il ciclo continui per la seconda volta, `C` deve essere strettamente maggiore di 1[cite: 92].
  * PC Aggiornata: `C > 1 && A[0] >= 0`[cite: 92].
* **Linea 7:** Stato degli step aggiornato: `S = 2`[cite: 93].
* **Linea 8 (Il punto critico):** Viene campionato l'elemento all'índice `i = 1`. Il valore simbolico associato ad `amount` è `A[1]`[cite: 93]. È qui che, se non imponiamo artificialmente il vincolo sulla lunghezza dell'array, rischiamo il buffer overflow intercettato dal professore.

## Domande di difesa probabili (Roleplay per l'Orale)

1. **Professore:** "Signor Riva, nella sua risposta all'esercizio lei ha concluso che l'accesso alla riga 8 è sicuro, ma io le ho scritto nei commenti che un Buffer Overflow è possibile se l'array ha un solo elemento. Chi ha ragione e perché?"
   **Risposta:** "Ha perfettamente ragione lei, professore. Nella mia analisi ho commesso l'errore di dare per scontata la precondizione esterna `count <= transactions.length`. Guardando però il puro codice della riga 6, il ciclo controlla unicamente che `i < count`. Se l'array ha un solo elemento e `count = 2`, la Path Condition simbolica accumulata alla seconda iterazione è `C > 1`, la quale permette perfettamente all'indice `i` di assumere il valore `1`. Poiché l'indice `1` viola il limite di un array di dimensione 1, l'analisi formale del codice rivela una vulnerabilità reale di Buffer Overflow, che si corregge inserendo il controllo esplicito sui confini dell'array nella guardia del `while`."

2. **Professore:** "Mi spieghi come ha calcolato il valore simbolico di `isNegative` alla riga 10 della prima iterazione. Perché ha scritto `A[0] < 0`?"
   **Risposta:** "Il calcolo avviene applicando il principio della sostituzione all'indietro dello stato. Alla linea 9, la variabile `balance` ha accumulato il valore del primo elemento dell'array, modificando il suo stato in `A[0]`. Di conseguenza, quando la linea 10 valuta l'espressione condizionale `balance < 0`, il motore simbolico sostituisce la parola `balance` con la sua espressione algebrica corrente, ricavando l'espressione puramente simbolica `A[0] < 0` da inserire nel registro."

3. **Professore:** "A cosa serve l'operazione ternaria che ha menzionato nelle risposte del foglio rispetto all'universo degli SMT Solver?"
   **Risposta:** "La formula di verifica dell'oracolo per il buffer overflow cerca di determinare se esiste un caso in cui la Path Condition è vera ma l'indice è fuori dai confini. Inviamo all'SMT Solver la formula `PC && !(0 <= I < transactions.length)`. Se il solver risponde `UNSAT`, significa che le regole del codice impediscono il bug. Se risponde `SAT`, come nel caso in cui l'array ha lunghezza 1 e non ci sono controlli protettivi, il solver non solo ci dice che il bug esiste, ma ci sputa fuori i valori concreti esatti dei parametri per riprodurre il crash in Java."
