## La traccia in breve

L'obiettivo dell'assignment era progettare e applicare un'analisi del flusso di dati (Data Flow Analysis) per il programma `generateSummary` per verificare staticamente che tutte le variabili siano sempre inizializzate prima di essere lette, rilevando eventuali anomalie. La soluzione richiede l'identificazione dell'analisi adatta, la definizione dei set gen/kill, la descrizione del criterio di rilevamento degli errori, la tabella di calcolo dei punti fissi passo-passo e l'indicazione della riga difettosa.

## Il codice sotto test

```java
public class ReportGenerator {
  public static int generateSummary(int[] values, int cutoff) { // 3
    int idx = 0;                                               // 5
    int count = values.length;                                 // 6
    int processed = 0;                                         // 7

    if (cutoff <= 0) {                                         // 9
      return -1;                                               // 10
    }

    if (count > 0) {                                           // 13
      int sum = 0;                                             // 14
    }

    while (idx < count) {                                      // 17
      int val = values[idx];                                   // 18
      if (val >= cutoff) {                                     // 20
        processed++;                                           // 21
      } else {                                                 // 22
        processed += 0;                                        // 23
      }
      idx++;                                                   // 26
    }

    if (processed > count) {                                   // 29
      processed = count;                                       // 30
    }

    return sum + processed;                                    // 33
  }
}
```

## La logica del Control Flow Graph (CFG)

Prima di applicare qualsiasi formula matematica, è indispensabile mappare il codice sotto forma di grafo (il Control Flow Graph visibile a pagina 3 del PDF).

*Cosa dire all'orale:* Il CFG scompone il programma in nodi decisionali ed esecutivi, tracciando con precisione i rami True (T) e False (F). Questo passaggio è fondamentale perché la Data Flow Analysis lavora sulla topologia dei cammini. Senza un CFG non potremmo identificare i predecessori di un nodo (`pred(n)`), l'unione dei cammini lineari, i cicli di ritorno (il backedge che da riga 26 risale a riga 17) o i punti in cui flussi separati tornano a fondersi (come le righe 17 e 33).

## Istanziamento dell'Analisi: Gen, Kill e Boundary Conditions

Per intercettare le letture a variabili non inizializzate, ho adattato l'algoritmo classico della **Avail Analysis (Forward, All-paths)**. Nella teoria pura l'Avail traccia la disponibilità delle espressioni matematiche, ma modificando la semantica dei set è possibile istanziarla direttamente sulla sicurezza delle variabili.

### Set Gen: $gen(n) = \{x \mid x \in def(n)\}$
Un nodo $n$ genera la "disponibilità" (ovvero l'avvenuta inizializzazione) di una variabile `x` se in quella specifica riga di codice la variabile viene definita o riceve un assegnamento ($def(n)$). 
- *Esempio:* Al nodo 5 (`int idx = 0;`), l'azione scrive sulla lavagna dell'analizzatore che `idx` è inizializzata, quindi $gen(5) = \{idx\}$.

### Set Kill: $kill(n) = \emptyset$
*Punto chiave d'esame:* A differenza dell'Avail classica (dove un assegnamento uccide le espressioni che contengono la variabile modificata), in questa analisi il set Kill è **tassativamente vuoto per ogni nodo**. La logica è semplice: stiamo tracciando lo stato di "essere inizializzato". In Java, una volta che una variabile riceve un valore iniziale, essa rimane inizializzata per tutto il resto del programma. Non esistono istruzioni nel linguaggio che possano de-inizializzare o cancellare una variabile dalla memoria primitiva per farla tornare allo stato `uninitialized`.

### Boundary Condition: $Avail(entry) = \{values, cutoff\}$
È la condizione al contorno che stabilisce lo stato iniziale all'ingresso del metodo (nodo `entry`). I parametri formali dichiarati nella firma della funzione (`values` e `cutoff`) sono considerati inizializzati per definizione, poiché è compito del chiamante passare dei valori reali. Tutte le altre variabili locali del metodo non compaiono in questo insieme di partenza.

### Cos'è il set Use(n) e come si rileva l'errore?
Il set $use(n)$ indica l'insieme delle variabili che vengono *lette* (utilizzate) all'interno del nodo $n$. 
L'anomalia viene intercettata matematicamente applicando la sottrazione insiemistica:
$$use(n) \setminus Avail(n) \neq \emptyset$$
*Significato logico:* Prendo le variabili che il codice tenta di leggere in quel punto ($use(n)$) e tolgo quelle che l'analisi mi garantisce essere sicuramente inizializzate ($Avail(n)$). Se l'insieme risultante contiene ancora qualcosa (non è vuoto), significa che il programma sta leggendo una variabile potenzialmente priva di valore iniziale.

## La Tabella dei Punti Fissi e la Derivazione Nodo per Nodo

La tabella riportata nel punto 4 del PDF rappresenta l'applicazione iterativa delle due equazioni cardine della DFA su ogni statement, partendo dall'alto e procedendo verso il basso (Forward).

1. **L'equazione di Join (Fusione dei cammini):**
   $$Avail(n) = \bigcap_{m \in pred(n)} AvailOut(m)$$
   Prima di valutare una riga $n$, l'analizzatore guarda tutti i suoi predecessori immediati (`pred(n)`). Trattandosi di un'analisi *All-paths*, applica l'**intersezione** ($\cap$): una variabile è considerata inizializzata all'ingresso del nodo $n$ solo se era stata inizializzata in *tutti* i percorsi che portano a quel nodo. Se un percorso non la contiene, l'intersezione la cancella.
   
2. **L'equazione di Trasferimento (Uscita dal nodo):**
   $$AvailOut(n) = (Avail(n) \setminus kill(n)) \cup gen(n)$$
   L'insieme in uscita dal nodo è calcolato prendendo l'ingresso ($Avail(n)$), togliendo il $kill(n)$ (che è vuoto) e aggiungendo il $gen(n)$ della riga corrente.

### Esempio di calcolo passo-passo sui punti critici:

- **Al nodo 14:** Arriva l'ingresso delle righe precedenti dove sono attive `{V, C, I, N, P}` (ovvero values, cutoff, idx, count, processed). La riga 14 esegue `int sum = 0;`, quindi $gen(14) = \{S\}$. L'output del nodo diventa $AvailOut(14) = \{V, C, I, N, P, S\}$.
- **Al nodo 17 (Join del ciclo):** I predecessori di 17 sono il nodo $13_F$ (il cammino che salta l'if di riga 13), il nodo 14 (il corpo dell'if) e il nodo 26 (la fine del ciclo while). Calcolando l'intersezione:
  $$AvailOut(13_F) \cap AvailOut(14) \cap AvailOut(26)$$
  Poiché nel cammino che passa da $13_F$ la variabile `sum` ($S$) non è mai stata generata, essa viene tagliata fuori dall'intersezione. Pertanto, l'ingresso al ciclo risulta $Avail(17) = \{V, C, I, N, P\}$. La variabile `sum` viene "persa" per tutta la durata del ciclo.
- **Al nodo 33 (Il punto di fallimento):** La riga esegue `return sum + processed;`, di conseguenza il set di uso è $use(33) = \{sum, processed\}$. L'insieme calcolato in ingresso al nodo tramite l'intersezione dei suoi predecessori finali è $Avail(33) = \{V, C, I, N, P\}$. 
  Applicando il criterio di errore:
  $$use(33) \setminus Avail(33) = \{sum, processed\} \setminus \{values, cutoff, idx, count, processed\} = \{sum\}$$
  Dato che il risultato contiene $\{sum\}$ e non è vuoto, l'analisi dimostra formalmente che la riga 33 tenta di leggere una variabile non inizializzata. Il cammino critico che scatena il bug (triggering path) è quello in cui `count <= 0`, che impedisce l'esecuzione sia dell'if a riga 13 sia del corpo del while, arrivando direttamente al return finale con la variabile `sum` priva di allocazione.

## Domande di difesa probabili

1. **Perché per trovare le variabili non inizializzate hai usato un approccio all-paths (intersezione) invece della Reach analysis classica (unione)?**
   *Cosa dire:* Perché l'inizializzazione richiede una garanzia assoluta. Devo essere certo che la variabile sia definita in *tutti* i cammini possibili. Se usassi l'unione (any-path), basterebbe che la variabile fosse inizializzata in un solo ramo fortunato dell'if per far credere all'analisi che sia sicura ovunque, nascondendo l'errore presente negli altri cammini scoperti.

2. **Cosa succede all'insieme delle variabili disponibili all'ingresso del nodo 17 e perché sum viene esclusa?**
   *Cosa dire:* Il nodo 17 riceve il flusso da più rami. Essendo un'analisi all-paths, calcolo l'intersezione delle uscite dei predecessori. Poiché nel cammino che salta il blocco della riga 13 la variabile `sum` non viene mai generata, essa non è presente in tutti gli insiemi di arrivo. L'intersezione cancella tutto ciò che non è comune, escludendo legittimamente `sum`.

3. **Perché il set Kill è stato impostato a vuoto per ogni statement del programma?**
   *Cosa dire:* Perché l'analisi monitora unicamente la proprietà di "avvenuta inizializzazione". In Java, una volta che una variabile locale riceve un valore iniziale, essa è inizializzata per sempre. Eventuali assegnamenti successivi modificano il valore memorizzato, ma non invalidano lo status di sicurezza della variabile. Non essendoci istruzioni in grado di riportare la variabile allo stato uninitialized, nessun nodo ha la capacità di uccidere questa informazione.

4. **In cosa differisce l'uso dell'Avail Analysis in questo esercizio rispetto all'applicazione classica descritta nel libro di testo?**
   *Cosa dire:* Nella teoria classica l'Avail analizza le *espressioni matematiche* per evitare che la CPU esegua calcoli duplicati, e il set Kill elimina le espressioni quando cambiano i loro operandi. In questo assignment, l'analisi è stata traslata ed istanziata direttamente sulle *variabili* per monitorare la sicurezza di lettura dello stato di inizializzazione, azzerando di conseguenza il set Kill.
