## La traccia in breve

Derivare i grafi di **control dependence** e **data dependence** del programma `rangeSearch`. I nodi devono contenere l'identificatore di riga indicato nel programma. La soluzione deve essere simile ai grafi visti a lezione (esempio GCD di Euclide). Suggerimento della traccia: usare uno strumento come draw.io. Più la parte di critica al GAI (le tre domande: query usata, risultato del GAI, commento sulla validità e differenze).

## Il codice sotto test

```java
public class IndexRange {
  public static int[] rangeSearch(int[] a, int loKey, int hiKey) {  // 2
    if (a == null || a.length == 0)        // 3
      return null;                          // 4
    if (loKey > hiKey) {                    // 5
      int temp = loKey;                     // 6
      loKey = hiKey;                        // 7
      hiKey = temp;                         // 8
    }
    int firstIndex = -1;                    // 10
    int lastIndex  = -1;                    // 11
    int i = 0;                              // 12
    while (i < a.length) {                  // 13
      if (a[i] >= loKey && a[i] <= hiKey) { // 14
        if (firstIndex == -1)               // 15
          firstIndex = i;                   // 16
        lastIndex = i;                      // 17
      }
      i = i + 1;                            // 19
    }
    if (firstIndex == -1) {                 // 21
      return null;                          // 22
    } else {                                // 23
      int[] result = new int[2];            // 24
      result[0] = firstIndex;               // 25
      result[1] = lastIndex;                // 26
      return result;                        // 27
    }
  }
}
```

## Cosa ho prodotto

Due grafi separati, entrambi con i nodi numerati per riga come richiesto dalla traccia:

- **Control Dependence Graph** - ad albero: la radice è l'intestazione del metodo (2), da cui pendono le istruzioni eseguite incondizionatamente; i nodi decisione (`if` 3, `if` 5, `while` 13, `if` 14, `if` 15, `if` 21) controllano le istruzioni dei rispettivi corpi.
- **Data Dependence Graph** - gli archi vanno da ogni definizione all'uso che raggiunge, etichettati con la variabile (`loKey`, `hiKey`, `temp`, `firstIndex`, `lastIndex`, `i`, `result`, `a`).

## Perché è strutturata così

1. **Due grafi distinti, come a lezione.**
   *Cosa dire:* la traccia chiede entrambi i tipi di dipendenza, che sono concetti diversi: il grafo di controllo mostra l'annidamento (cosa sta dentro quale decisione), quello dei dati mostra il flusso dei valori (quale definizione alimenta quale uso). Tenerli separati segue l'impostazione del corso (esempio GCD).

2. **Nodi etichettati per riga.**
   *Cosa dire:* la traccia lo richiede esplicitamente ("the name of the nodes shall contain the line statement identifier"). Ho usato la numerazione del listato (2, 3, 4, 5, …) così ogni nodo è tracciabile al codice.

3. **Archi dati etichettati con la variabile.**
   *Cosa dire:* ogni du-pair porta il nome della variabile che fluisce, come nell'esempio GCD. Esempi chiave nel mio grafo:
   - `loKey`/`hiKey` definiti all'header (2) e usati nello swap (5–8) e nel confronto (14);
   - lo **swap** 6→7→8: `temp` definito a 6 e usato a 8, `loKey`/`hiKey` che si incrociano;
   - `firstIndex` definito a 10, ridefinito a 16, usato a 15, 21, 25;
   - `lastIndex` definito a 11, ridefinito a 17, usato a 26;
   - `i` definito a 12, ridefinito a 19, usato a 13, 14, 16, 17;
   - `result` definito a 24, usato a 25, 26, 27.

4. **Attenzione ai def-clear path con le ridefinizioni.**
   *Cosa dire:* `firstIndex`, `lastIndex` e `i` vengono ridefiniti dentro il ciclo. Ho tracciato gli archi dati tenendo conto che una ridefinizione può "uccidere" la precedente lungo certi cammini - è il punto più delicato del data dependence graph su questo programma.

### Data Dependence → corretto, con due punti da verificare

La gran parte degli archi coincide col prof ed è giusta:

- **swap** temp/loKey/hiKey tra 6, 7, 8 ✓
- **`a`** dalla radice 2 → 3, 13, 14 ✓
- **`loKey`/`hiKey`** → 14 (e verso lo swap) ✓
- **`i`**: 12 → {13, 14, 16, 17, 19} e 19 → 13 (il giro del ciclo) ✓

:::caution[I due punti da controllare - variabili ridefinite nel ciclo]
Il rischio, su questo programma, è uno solo: le variabili **definite due volte** (una fuori, una dentro il ciclo) devono avere archi da *entrambe* le definizioni verso *ogni* loro uso, perché entrambe lo raggiungono lungo cammini diversi (se il ciclo non entra mai vale la def iniziale; se entra, quella interna).

1. **`firstIndex`** - definito a **10** (`-1`) e a **16** (`= i`); usato a **15, 21, 25**.
2. **`lastIndex`** - definito a **11** (`-1`) e a **17** (`= i`); usato a **26**.
